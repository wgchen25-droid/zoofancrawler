# ZooFanCrawler

ZooFanCrawler is a small, polite multi-source crawler for news articles from
configured official zoo websites. `config/zoos.yaml` is the runtime registry
for the completed Phase0 v0.1 import: **73 enabled zoo rows**, **116 source
rows**, and **63 enabled source checks** (44 article-capable plus 19
`registry_only` health checks). The authoritative membership snapshot is
[`data/zoofan_phase0_zoo_list_v0_1.md`](data/zoofan_phase0_zoo_list_v0_1.md),
SHA-256
`6c470233559657cc39e91c50ba5c12786c33af05bbe13c95c91b317ff76d63dd`.
The four rows without a verified official website remain explicitly present
as `SOURCE_NOT_FOUND`/`not_found` records; no directory, municipal, social, or
search-result URL was promoted to a crawl source. See the auditable [roster
summary](reports/zoo-list-summary.md).

The architecture and development boundaries are described in
[PROJECT.md](PROJECT.md) and [AGENTS.md](AGENTS.md).

The pipeline is deliberately layered: configuration and domain records feed
source discovery, URL policy, fetching, parsing, crawler orchestration, and
SQLite storage. The Flask Dashboard is a read-only view of the resulting
database. A source or article failure is recorded and isolated so later
configured sources can continue.

## Quick start

Use Python 3.9+ and install the declared dependencies:

```sh
python3 -m venv .venv
. .venv/bin/activate
python3 -m pip install -r requirements.txt
```

Validate the registry without network or database access:

```sh
python3 cli.py --config config/zoos.yaml validate-config --json
```

For a persistent crawl, use the same database path for crawling, reporting,
and Dashboard inspection. The default crawl database is `:memory:` and is
lost when the process exits.

## CLI

Global options such as `--config` and `--log-level` precede the subcommand.
The current CLI accepts the following commands:

```sh
# Global options (`--config`, `--log-level`) come before the subcommand.
# Crawl the enabled registry (legacy positional form and explicit form).
python3 cli.py --config config/zoos.yaml crawl all --db data/zoofan.db
python3 cli.py --config config/zoos.yaml crawl --all --db data/zoofan.db

# Select one configured zoo; group selection uses the imported Phase0 groups.
python3 cli.py --config config/zoos.yaml crawl --zoo zoo-berlin --db data/zoofan.db
python3 cli.py --config config/zoos.yaml crawl --all --db data/zoofan.db

# Run one scheduled batch, or start the six-hour scheduler.
python3 cli.py --config config/zoos.yaml scheduler --db data/zoofan.db --once
python3 cli.py --config config/zoos.yaml scheduler --db data/zoofan.db --hours 6

# Build the five read-only report artifacts from an existing database.
python3 cli.py --config config/zoos.yaml build-acceptance-report \
  --db data/zoofan.db --output-dir reports

# Run the live end-to-end workflow (also available as `acceptance`).
python3 cli.py endgoal
make endgoal

# Inspect the same database locally.
python3 cli.py --config config/zoos.yaml dashboard --db data/zoofan.db \
  --host 127.0.0.1 --port 8000
python3 cli.py --config config/zoos.yaml control --db data/zoofan.db \
  --host 127.0.0.1 --port 8001
```

Zoo selection aliases include the preserved `berlin`, `zoo-berlin`, `koeln`,
`koeln-zoo`, `cologne`, `gaia`, and `gaiazoo` forms; all other IDs and slugs
are resolved from the loaded 73-row registry. Group selection uses only the
explicit Phase0 `groups` values (`core30`, `regional_lab`, and their five
subgroups); no group is inferred from source availability.

`./start.sh` starts Dashboard and control together on `127.0.0.1`, using the
same persistent `data/zoofan.db`; set `DASHBOARD_PORT`, `CONTROL_PORT`, or
`ZOOFAN_NO_OPEN=1` as needed. It never crawls or deletes the database.

## Configuration and status vocabulary

`config/zoos.yaml` is the single source of truth. An enabled zoo record may
contain:

| Field | Meaning |
| --- | --- |
| `id` | Required stable identity. |
| `slug`, `name` | Selection key and display name. |
| `website_url` | Verified official HTTP(S) URL; intentionally omitted for the four Phase0 no-site rows. |
| `country_code`, `language` | Validated ISO country and primary language codes. |
| `region`, `city` | Optional display metadata. |
| `groups` | Explicit Phase0 group memberships; multiple values are preserved. Every row has exactly two memberships. |
| `source_status` | Configuration-level evidence status; the static distribution is `success` 27, `partial` 11, `robots_disallowed` 13, `source_not_found` 7, `unsupported` 4, `not_found` 4, `blocked` 3, `configured` 2, and `javascript_required` 2. It is not a live result. |
| `list_provenance` | Traceable source/version note for roster membership. |
| `enabled`, `metadata` | Scheduling and non-policy display metadata. |
| `sources` | Nested source records for this zoo. |

Each source has a stable `id`, `name`, `kind` (or matching `adapter`),
official `url`, optional `language`/`enabled`, and a `config` mapping. Policy
and parser configuration may include `official_host`, article selectors,
pagination limits, `article_allow`/`allow_regex`, `exclude_regex`, and narrow
navigation patterns. Source URLs and targets are normalized with
`zoofan.normalization.normalize_url`; source and article URLs must also pass
the official-domain and allow/exclude URL policy.

The canonical adapter/status vocabulary has eight kinds: `rss`, `atom`,
`sitemap`, `archive`, `json_api`, `custom_adapter`, `registry_only`, and
`unsupported`. No site-specific adapter was added. The article-capable generic
kinds actually reused by Phase0 are `rss`, `sitemap`, and `archive`; adding
`registry_only` for health checks makes four operational source shapes.
`json_api` and `custom_adapter` remain shared framework capabilities covered by
deterministic tests, while `html` and `news_archive` remain archive aliases.
`registry_only` deliberately produces no article candidates.
Runtime source/run classifications include successful, no-items, partial,
failed, HTTP, robots, timeout, DNS/TLS, parse, blocked, unsupported,
configuration, `date_parse_error`, `content_parse_error`, and
`javascript_required` outcomes.

The checked-in `artifacts/endgoal-report.json` and
`artifacts/dashboard-acceptance.png` are historical snapshots. They are not
the fresh 73-zoo evidence above and must not be described as the current
Phase0 acceptance artifacts.

## Fetching and safety boundaries

Normal network requests go through `Fetcher`. Robots checking is enabled by
default and fail-closed: an unavailable or unparseable robots response, a
disallowed target, or a disallowed redirect stops that request. Requests keep
per-domain pacing, bounded retries/backoff, `Retry-After` handling, and a
redirect limit. Source discovery uses server-rendered RSS/Atom, sitemap, or
configured archive HTML; Playwright is used for Dashboard/static report smoke
only, not as a hidden crawler fallback.

The crawler uses a bounded response/page cache with a 30-second default TTL.
Requests are serialized one-at-a-time per domain (`per-domain=1`) and the
overall crawl is globally serial. Robots, pacing, bounded retries/backoff,
`Retry-After`, and redirect limits remain enforced.

`articles.raw_html` is untrusted capture evidence. It is never rendered by
the Dashboard or marked safe, and the report projection omits it. Displayed
article content is parsed and template-escaped. External links are emitted
only for HTTP(S) URLs with a network location and carry safe `rel` attributes;
displaying a link is not an additional official-domain authorization.

## SQLite schema and deduplication

`SQLiteStorage` currently uses **schema version 7** (`PRAGMA user_version` and
`schema_meta`). Schema creation and migration are additive and idempotent:
legacy databases are upgraded in place, necessary fields are backfilled, and
indexes are created with `IF NOT EXISTS`. The storage boundary owns all SQLite
writes.

The schema contains `zoos`, `sources`, `articles`, `article_discoveries`,
`crawl_runs`, `crawl_run_stats`, `article_zoo_identities`,
`crawl_zoo_results`, and `schema_meta`, including raw URL and timestamp
evidence needed for runtime classification. Article identity is protected by
canonical URL, normalized URL, and a composite `content_identity_key` derived
from the content hash and normalized title. The content hash remains evidence
and is not globally unique: `content_hash` hashes normalized parsed article
identity content, while `html_hash` hashes the raw response bytes. Discovery
relationships retain multiple sources without copying an article row.

## Acceptance and reports

Offline deterministic regression tests use injected transports/fetchers and
SQLite fixtures:

```sh
PYTHONWARNINGS=error python3 -m pytest -q
```

The current quality-gate evidence is **588 passed, 0 skipped** under
`PYTHONWARNINGS=error`. Ruff, mypy, strict configuration validation,
compileall, and `git diff --check` are separate checks. The deterministic
groups can be run with the explicit taxonomy below;
strict validation is
`python3 cli.py --config config/zoos.yaml validate-config --json`.

| Make target | Exact test modules | Scope |
| --- | --- | --- |
| `config-tests` | `tests/test_config.py` | Registry/schema/config validation |
| `fixture-tests` | `tests/test_fetcher.py`, `tests/test_normalization.py`, `tests/test_parsers.py`, `tests/test_url_policy.py` | Deterministic transports, parser fixtures, URL/date normalization |
| `integration-tests` | `tests/test_cli.py`, `tests/test_control.py`, `tests/test_crawler.py`, `tests/test_dashboard.py`, `tests/test_failure_isolation.py`, `tests/test_live_smoke.py`, `tests/test_module_cli.py`, `tests/test_start_script.py`, `tests/test_storage.py` | Orchestration, persistence, UI, CLI, live-smoke contract, and failure boundaries |
| `golden-tests` | `tests/test_endgoal.py`, `tests/test_reporting.py` | Acceptance projection and Phase0/endgoal contracts |
| `quality-tests` | `tests/test_packaging.py`, `tests/test_quality_gates.py` | Package-data and Makefile taxonomy/tooling/command contracts |

These five groups partition every `tests/test_*.py` module exactly once;
`make test` remains the complete-suite command. The quality-gate contract test
parses the explicit lists and checks that no test module is omitted or assigned
to multiple groups. These groups use local fixtures/fakes and do not perform
live network access.

The wheel/package-data contract is covered by `tests/test_packaging.py`:
packaged config, Jinja templates, and static assets are present at runtime.

`build-acceptance-report` is intentionally guarded: it rejects an empty,
invalid, or schema-less database instead of returning a misleading report
success. The repository's `data/zoofan.db` may be a zero-byte placeholder, so
provide a real crawl database explicitly, for example:

```sh
make build-acceptance-report \
  DB="$LIVE_DB" \
  REPORT_DIR=/tmp/zoofancrawler-reports
```

For one non-recursive offline gate, provide an explicit usable database. It
runs config validation, Ruff, mypy, the complete pytest suite, and report
generation directly:

```sh
make offline-gates \
  OFFLINE_DB="$LIVE_DB" \
  REPORT_DIR=/tmp/zoofancrawler-reports
```

`offline-gates` refuses an omitted or zero-byte `OFFLINE_DB`; it does not call
another Make target and it never performs a crawl. The generated report path
can be set to `reports` when updating repository deliverables, or to a
temporary directory for a read-only verification.

The taxonomy includes `tests/test_live_smoke.py` in the integration group and
`tests/test_packaging.py` in the quality group. The live-smoke tests use strict
candidate/page bounds; they do not turn the offline suite into an unbounded
network crawl. The final full-suite result is 588 passed and 0 skipped with
warnings treated as errors.

`make endgoal` (or `python3 cli.py endgoal`) is the repository's networked
acceptance workflow: it runs tests, performs two real crawls against every
enabled configured zoo/source, checks persistence, URL/official-domain policy,
raw HTML/hash evidence, source/run statistics and deduplication, then
smoke-tests Dashboard routes and the static acceptance report in a real
Playwright browser. It requires network access, reachable official sites, and
an available Chromium installation. It removes and recreates only the
explicitly named `data/acceptance.db` (and SQLite sidecars), not other local
databases. The documented Phase0 evidence above was produced by an equivalent
fresh temporary double crawl; do not infer that `make endgoal` regenerated the
tracked root artifacts.

The bounded live-smoke command is intentionally capped:

```sh
python3 cli.py --config config/zoos.yaml crawl --all \
  --db /tmp/zoofancrawler-live-smoke.sqlite --live \
  --since-days 7 --max-candidates-per-source 1 --max-pages 1
```

To reproduce a fresh, unbounded two-round crawl in an isolated temporary
database, then build and serve the static report, run:

```sh
LIVE_DIR="$(mktemp -d /tmp/zoofancrawler-phase0-live.XXXXXX)"
LIVE_DB="$LIVE_DIR/acceptance.db"
python3 cli.py --config config/zoos.yaml crawl all --db "$LIVE_DB" | tee "$LIVE_DIR/run-1.json"
python3 cli.py --config config/zoos.yaml crawl all --db "$LIVE_DB" | tee "$LIVE_DIR/run-2.json"

python3 cli.py --config config/zoos.yaml build-acceptance-report \
  --db "$LIVE_DB" --output-dir reports
python3 -m http.server 8765 --directory reports/latest
```

The read-only `build-acceptance-report` command derives all five files from

`artifacts/dashboard-acceptance.png` only after Dashboard smoke reaches its
home page. A failed live run is diagnostic evidence, not a reason to replace
the real crawl with fixtures.

## Scope and extension

The Phase0 roster is now the authoritative 73-row membership boundary. Future
changes require a new versioned roster/provenance record and deterministic
config, URL-policy, parser, crawler, storage, and failure-isolation tests before
live validation. Do not infer members from capacity discussions, article data,
or unrelated source URLs. Preserve the four no-site rows until an official
endpoint is explicitly verified; do not fabricate a URL to improve coverage.

Scaling the registry remains subject to endpoint rate limits, changing CMS
markup, source-policy maintenance, serial network latency, SQLite contention,
and longer live acceptance runs. A production queue, distributed scheduler,
and broad observability backend are outside the current scope.
