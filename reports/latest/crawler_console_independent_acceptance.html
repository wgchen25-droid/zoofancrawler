4. Blocker B1 — Console API thread-unsafe (spurious 404 / empty results under parallel requests)

BLOCKER Severity: Blocker. Confidence: reproduced by V4 Pro and independently by Flash C; root cause confirmed in code.

Evidence chain

  1. Runtime (HTTP): 
    # V4 Pro server on a copy of the real legacy DB (data/zoofan.db, 3 runs, 73 zoos)
$ seq 1 6 | xargs -P 6 -I{} curl -s -o /dev/null -w '%{http_code}\n'     http://127.0.0.1:8105/api/crawl-runs/5738c3f9ba034c7cb597067fb781242d/zoos
1×200, 5×404   ({"error":{"code":"not_found","message":"5738c3f9...242d"}})
$ seq 1 6 | xargs -P 6 -I{} curl -s "http://127.0.0.1:8105/api/crawl-runs?limit=5"
5× count:0 (empty), 1× count:3   — the DB has 3 runs
$ sequential: all 200 with correct data
  2. Runtime (browser): the console's own JS fires parallel requests — console_base.html:401 (Overview: Promise.all([statusUrl, runsUrl])), :581 (Run Detail: Promise.all of 4 fetches), :622 (Zoo Detail: 2 fetches). Result (Playwright, V4 Pro): Run Detail shows Loading run details… and a Retry error box; 3 of the 4 API fetches returned 404 in the server log. Screenshot:

Run Detail page under normal browser load: RUN SUMMARY stuck at "Loading run details…", "Zoo results … Retry" error region. The run 5738c3f9ba034c7cb597067fb781242d exists in the DB.

  1. Root cause (code):
    • zoofan/console_repository.py:541-572 — ConsoleRepository.__init__ borrows or opens one sqlite3.Connection kept for the repository's lifetime.
    • zoofan/console_api.py:565-568 — the service/repository is cached per-app (current_app.extensions["_crawler_console_default_service"]), so every Flask request thread shares that single connection.
    • zoofan/dashboard.py:146 — app.run(...) serves requests with threads (Werkzeug default), and the console JS deliberately fetches in parallel.
    • Two threads interleaving cursors on one connection raise sqlite3.ProgrammingError; console_repository.py:598-599 swallows sqlite3.Error in _columns() and returns [] → table treated as missing → get_run() (:884-889) returns None → _require_parent() (console_api.py:647-648) raises ConsoleNotFoundError → 404; list endpoints return empty.
    • Control group: the legacy dashboard routes survive 5×200 under parallel load because dashboard.py:166-174 get_db() gives each request its own connection. Only the console repository shares one.
  2. Why the developer report missed it: its API/UI checks were sequential requests against tiny in-memory fixtures (sub-millisecond queries → interleaving never occurs). The defect manifests on real data volumes (100 MB legacy DB, slow queries) under the normal browser access pattern. This is exactly why the developer report's Known Limitations line ("deterministic in-memory fixtures") matters.

Impact

  • Required pages Overview, Run Detail, Zoo Detail — 3 of the 7 console pages — intermittently fail or show wrong empty states in normal use; Events/Articles single-fetch pages can also fail when their fetch races with polling refreshes.
  • Silent data-quality hazard: empty lists look identical to a genuinely empty database.
  • Applies to the shipped command (python3 cli.py dashboard …) and to any threaded WSGI deployment; not an artifact of the dev server.

Suggested fix direction (not applied — reviewers are read-only)

  • Give every request its own read-only connection (mirror dashboard.get_db()'s request-scoped pattern, query_only=ON), or serialize repository access with a lock; never share one connection across threads.
  • Do not swallow sqlite3.Error as "table missing" — distinguish introspection errors from absent schema so failures become 503, not false 404/empty.
  • Add a deterministic parallel-read regression test (e.g., ThreadPoolExecutor hitting the API via Flask test client or a live server) asserting all responses 200 with correct rows.
